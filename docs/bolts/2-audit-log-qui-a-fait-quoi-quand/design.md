# Design — Journal d'audit : qui a fait quoi, quand (#2)

## Approche

Deux mecanismes complementaires, pas un seul, parce que le ticket melange deux besoins differents. (1) Tracabilite de creation/modification "en place" : `Auditable` gagne `created_by`/`updated_by` (VARCHAR, username), renseignes automatiquement dans les hooks `@PrePersist`/`@PreUpdate` deja existants via `SecurityContextHolder.getContext().getAuthentication().getName()` (pas de `@EnableJpaAuditing`/`AuditorAware` a introduire, ca resterait coherent avec le style manuel deja en place dans `Auditable`). `Payment` n'etend pas `Auditable` (pas d'`updated_at` en base, jamais modifie en place) : il recoit son propre `created_by`, pose dans son `@PrePersist` existant. (2) Tracabilite d'evenements qui ne survivent pas a la ligne elle-meme : `CustomerService.delete`, `CreditSaleService.delete` et `ProductService.delete` font un **DELETE physique** (verifie dans le code), donc `created_by`/`updated_by` poses sur la ligne supprimee disparaissent avec elle — impossible de satisfaire le critere d'acceptation "suppression d'un client... historisee avec auteur + date" par colonnes seules. Il faut une table `audit_log` append-only, alimentee explicitement (pas de hook automatique) aux points d'appel sensibles cites par le ticket : suppression client, annulation de contrat, modification de prix produit. Le prix de cette approche a deux mecanismes est un peu plus de code (un service `AuditLogService` + des appels explicites) contre l'alternative "tout dans Auditable" qui est plus simple mais ne peut techniquement pas satisfaire le critere de suppression.

## Fichiers/modules impactes

Backend :
- `backend/src/main/java/com/creditflow/common/domain/Auditable.java` — ajout `createdBy`/`updatedBy` (String), renseignes dans `onCreate()`/`onUpdate()` via `SecurityContextHolder` (null-safe si pas d'authentification, ex. contexte batch/bootstrap).
- `backend/src/main/java/com/creditflow/payment/domain/Payment.java` — ajout `createdBy`, pose dans `onCreate()` existant.
- `backend/src/main/java/com/creditflow/common/domain/AuditLog.java` (nouveau) — entite `@Entity @Table(name="audit_log")` : `id`, `entityType` (String, ex. CUSTOMER/CREDIT_SALE/PRODUCT), `entityId`, `entityLabel` (ex. reference contrat / nom client, pour affichage sans re-jointure sur une ligne parfois supprimee), `action` (String, ex. DELETE/CANCEL/PRICE_UPDATE), `details` (TEXT, ex. "Prix credit: 150 000 -> 165 000"), `actor` (username), `createdAt`.
- `backend/src/main/java/com/creditflow/common/repository/AuditLogRepository.java` (nouveau) — `findByEntityTypeAndEntityIdOrderByCreatedAtDesc`.
- `backend/src/main/java/com/creditflow/common/service/AuditLogService.java` (nouveau) — une methode `record(entityType, entityId, entityLabel, action, details)`, lit l'utilisateur courant via `SecurityContextHolder`, appelee explicitement (pas de hook JPA generique — trop de bruit pour des updates non sensibles).
- `backend/src/main/java/com/creditflow/common/dto/AuditLogResponse.java` (nouveau).
- `backend/src/main/java/com/creditflow/common/web/AuditLogController.java` (nouveau) — `GET /api/audit-log?entityType=&entityId=`, authentifie (tout role), pas de restriction ADMIN supplementaire (coherent avec le fait que les GET restent ouverts ailleurs dans le code).
- `backend/src/main/java/com/creditflow/customer/service/CustomerService.java` — `delete()` appelle `auditLogService.record("CUSTOMER", id, customer.getFullName(), "DELETE", null)` avant `customerRepository.delete(customer)`.
- `backend/src/main/java/com/creditflow/sale/service/CreditSaleService.java` — `cancel()` et `delete()` appellent `auditLogService.record("CREDIT_SALE", id, sale.getReference(), "CANCEL"/"DELETE", null)`.
- `backend/src/main/java/com/creditflow/product/service/ProductService.java` — `update()` compare `cashPrice`/`creditPrice` avant/apres ; si l'un des deux change, appelle `auditLogService.record("PRODUCT", id, product.getName(), "PRICE_UPDATE", "Prix credit: X -> Y")`.
- `backend/src/main/java/com/creditflow/payment/dto/PaymentResponse.java` — ajout `createdBy`.
- `backend/src/main/java/com/creditflow/payment/mapper/PaymentMapper.java` — mapping implicite de `createdBy` (deja sur l'entite, MapStruct le mappe sans `@Mapping` custom).
- `backend/src/main/java/com/creditflow/sale/dto/SaleResponse.java`, `backend/src/main/java/com/creditflow/customer/dto/CustomerResponse.java`, `backend/src/main/java/com/creditflow/product/dto/ProductResponse.java` — ajout `createdBy`/`updatedBy`.
- `backend/src/main/java/com/creditflow/sale/mapper/SaleMapper.java`, `backend/src/main/java/com/creditflow/customer/mapper/CustomerMapper.java`, `backend/src/main/java/com/creditflow/product/mapper/ProductMapper.java` — idem, mapping implicite (les champs existent deja sur Auditable, juste a exposer dans les DTO).
- `backend/src/main/resources/db/migration/V3__audit_columns.sql` (nouveau) — `ALTER TABLE credit_sales/products/customers ADD COLUMN created_by VARCHAR(80), ADD COLUMN updated_by VARCHAR(80)` ; `ALTER TABLE payments ADD COLUMN created_by VARCHAR(80)` ; `CREATE TABLE audit_log (...)`. Colonnes nullables (pas de NOT NULL : les lignes existantes n'ont pas d'auteur connu).
- Tests : `backend/src/test/java/com/creditflow/common/service/AuditLogServiceTest.java`, et complements sur les tests de service existants de `CustomerService`/`CreditSaleService`/`ProductService` (si presents — a verifier par le spec-writer) pour couvrir l'ecriture de l'audit_log et le remplissage de created_by.

Frontend :
- `frontend/src/types.ts` — ajout `createdBy?: string` sur `Sale`, `Customer`, `Product`, `Payment` ; nouveau type `AuditLogEntry { entityType, entityId, entityLabel, action, details, actor, createdAt }`.
- `frontend/src/api/endpoints.ts` — nouveau `auditLogApi.list(entityType, entityId)`.
- `frontend/src/pages/SaleDetailPage.tsx` — nouvelle section "Historique" (Card, pas de composant Tabs MUI dans le projet aujourd'hui — coherent avec le style page existant) listant `auditLogApi.list('CREDIT_SALE', saleId)` ; colonne "Enregistre par" ajoutee au tableau des paiements existant (payment.createdBy).
- `frontend/src/pages/CustomerDetailPage.tsx` — nouvelle section "Historique" listant `auditLogApi.list('CUSTOMER', customerId)`.
- `frontend/src/pages/PaymentsPage.tsx` — colonne "Enregistre par" si l'espace le permet (a confirmer par le spec-writer).

## Decisions cles

- **created_by/updated_by en VARCHAR (username), pas de FK numerique vers users.id** : le principal expose par `AppUserDetailsService`/`JwtAuthenticationFilter` est un `org.springframework.security.core.userdetails.User` standard, qui ne porte que le username (pas l'id numerique). Utiliser le username evite une requete `UserRepository` supplementaire dans un hook `@PrePersist`/`@PreUpdate` (qui n'a pas d'injection Spring) et decouple totalement l'audit du cycle de vie de `users` — meme si un User venait un jour a etre supprime physiquement (aujourd'hui exclu, voir #1), la chaine de caracteres resterait. Prix : si un compte est renomme un jour, l'historique affichera l'ancien username — non bloquant, aucune fonctionnalite de renommage n'existe.
- **Table audit_log dediee, remplissage explicite (pas de hook JPA generique automatique)** : necessaire car `CustomerService.delete`, `CreditSaleService.delete` et `ProductService.delete` font des suppressions physiques (verifie dans le code) — created_by sur la ligne ne survit pas a son propre DELETE. Alternative ecartee : intercepteur JPA generique sur tous les `@PreRemove`/`@PostUpdate` de toutes les entites auditables — retenu comme trop large (bruiterait l'historique avec des updates non sensibles comme un simple changement de stock) par rapport a ce que le ticket demande explicitement (suppression client, annulation contrat, modification prix).
- **ProductService.update() ne journalise que si le prix change reellement** (comparaison avant/apres cashPrice/creditPrice), pas a chaque modification de produit (stock, description, statut) — coherent avec le critere d'acceptation qui cible specifiquement "modification d'un prix produit", pas toute edition.
- **CreditSaleService.delete() (suppression physique d'un contrat sans paiement) journalisee au meme titre que cancel()** : non explicitement listee dans les criteres d'acceptation (qui ne citent que "l'annulation d'un contrat"), mais c'est aussi une disparition physique de ligne comme la suppression client — decision d'aligner par coherence ; a confirmer par le spec-writer si juge hors perimetre strict.
- **PaymentService.delete() ("annulation d'un versement", suppression physique) volontairement PAS journalisee dans audit_log** dans ce perimetre : le ticket ne le liste pas explicitement parmi les 4 actions sensibles citees (paiement enregistre = trace via created_by sur la ligne qui, elle, n'est pas supprimee en usage normal ; la suppression d'un paiement est un flux distinct). Signale en risque ci-dessous car c'est une incoherence potentielle avec l'esprit du ticket (un paiement supprime perd toute trace, y compris son created_by) — a trancher par le spec-writer.
- **Pas de @EnableJpaAuditing/AuditorAware** : le projet n'utilise pas les annotations Spring Data JPA Auditing (@CreatedBy/@LastModifiedBy), Auditable gere deja created_at/updated_at a la main. Ajouter l'infrastructure Spring Data Auditing pour seulement 2 nouvelles colonnes aurait ete disproportionne ; reutilisation du meme style manuel (SecurityContextHolder direct dans les hooks JPA existants).
- **Colonnes nullables, pas de backfill** : les lignes deja en base (creees avant la migration) auront created_by = NULL — accepte, aucune donnee d'auteur n'existe retroactivement pour les reconstruire.
- **Ecran "Historique" limite aux fiches contrat/client** (conforme au perimetre propose), pas de nouvelle vue produit : il n'existe aujourd'hui aucune ProductDetailPage (seule ProductsPage, une liste) — creer une page dediee juste pour afficher l'historique de prix serait hors perimetre. Le critere d'acceptation exige seulement que la modification de prix soit "historisee" (en base, via audit_log), pas qu'elle soit visible dans un ecran dedie.

## Risques / points d'attention

- **SecurityContextHolder dans un hook @PrePersist/@PreUpdate** : fonctionne pour tout flux passant par une requete HTTP authentifiee (y compris l'import legacy, dataimport/service/LegacyImportService, qui tourne sous le contexte de l'utilisateur ayant appele POST /api/import). Reste null pour tout code s'executant hors requete HTTP (ex. AuthService/AdminInitializer au bootstrap) — a gerer en null-safe dans Auditable.onCreate()/onUpdate(), jamais lever d'exception.
- **PaymentService.delete() non couvert par audit_log** (voir decision ci-dessus) : si le spec-writer estime que la suppression d'un paiement est une action sensible equivalente a l'annulation de contrat, il faudra l'ajouter — actuellement hors du perimetre litteral du ticket mais laisse un trou de tracabilite sur une operation financiere physique.
- **CustomerService.delete() supprime aussi le fichier photo** (fileStorageService.deleteByPublicUrl) — l'entree audit_log doit etre ecrite avant l'appel a customerRepository.delete() dans la meme transaction, pour eviter une incoherence si la suppression echoue apres coup (peu probable mais l'ordre des operations compte).
- **Volume de la table audit_log** : pas de pagination prevue cote GET /api/audit-log dans ce design (liste simple par entite, volumes attendus faibles — un contrat ou un client n'aura que quelques evenements). A revisiter si le besoin de pagination apparait en usage reel.
- **Colonnes updated_by sur credit_sales/products/customers seront aussi mises a jour par des actions non "sensibles"** (ex. PaymentService.recalculate() sauvegarde le contrat a chaque paiement, ce qui declenchera @PreUpdate et ecrasera updated_by avec l'auteur du dernier versement, pas forcement l'auteur de la derniere modification "metier" du contrat lui-meme) — comportement attendu et documente mais a ne pas confondre avec un historique complet : updated_by ne donne que le dernier auteur, pas la liste ; c'est audit_log qui porte la vraie granularite pour les 3 actions citees par le ticket.
- **Pas de test @WebMvcTest existant pour AuditLogController** (comme note dans le design #1, le projet n'a que des tests de service) — a prevoir from scratch par le spec-writer/codeur.

## Hors perimetre

- FK numerique users.id sur created_by/updated_by (choix de stocker le username, voir decisions).
- Journalisation de la suppression d'un paiement (PaymentService.delete) dans audit_log — signale en risque, pas implemente par defaut.
- Journalisation generique de toute modification (stock produit, notes client, etc.) — seules les 3 actions explicitement citees par le ticket ecrivent dans audit_log.
- Ecran d'historique dedie aux produits (pas de ProductDetailPage).
- Pagination/filtrage avance de audit_log (recherche globale, export).
- Reconstruction retroactive de created_by pour les lignes existantes (colonnes nullables, pas de backfill).
- Toute modification du flux JWT/SecurityContext existant (JwtAuthenticationFilter, AppUserDetailsService reutilises tels quels).
