# Design — Issue #65 : limitation de debit sur /api/auth/login

## Approche

Defense en deux couches independantes, chacune bon marche a operer sur une stack mono-instance (docker-compose.yml : un seul service backend, pas de Redis) : (1) nginx limite le debit de requetes par IP sur l'endpoint exact /api/auth/login via limit_req_zone (memoire locale au worker, suffisant en mono-instance) ; (2) applicatif ajoute un verrouillage temporaire par compte apres N echecs consecutifs (failed_login_attempts/locked_until sur users), qui protege un compte cible depuis plusieurs IP (contournement du (1)) et notamment le compte ADMIN vise par le ticket. Aucune lib de rate limiting (Bucket4j ou equivalent) n'est ajoutee au pom.xml : verifie absente aujourd'hui, et le besoin (compteur + timestamp par utilisateur, verifie a chaque login) se couvre avec deux colonnes SQL et un peu de logique dans AuthService, sans nouvelle dependance ni etat partage a operer. Prix de ce choix : pas de fenetre glissante sophistiquee (pas de compteur par minute lisse), juste un seuil brut plus verrou fixe, suffisant pour bloquer un brute-force scripte, pas pour du reporting fin d'attaques.

Le message d'erreur reste strictement identique dans les trois cas (compte inexistant, mot de passe errone, compte verrouille) : AuthenticationException donne "Identifiants invalides" (401), deja le comportement actuel de GlobalExceptionHandler.handleAuthentication pour les deux premiers cas (verifie, aucune regression a faire ici) et reutilise a l'identique pour le troisieme. C'est la decision la plus simple pour satisfaire le critere d'acceptation "le message ne permet pas de distinguer compte inexistant / mot de passe incorrect" sans introduire un nouvel oracle (un message "compte verrouille" revelerait aussi que le compte existe).

## Fichiers/modules impactes

Backend :
- backend/src/main/resources/db/migration/V20__users_login_lockout.sql (nouveau) — ajoute deux colonnes sur users : failed_login_attempts (INT NOT NULL DEFAULT 0) et locked_until (TIMESTAMP, nullable). Pas de GRANT supplementaire : V16__app_role_grants.sql accorde deja UPDATE sur users au role applicatif. users n'est pas soumise a RLS (V15__row_level_security.sql, confirme par le commentaire de V19__users_email.sql), aucune policy a toucher.
- backend/src/main/java/com/creditflow/auth/domain/User.java — deux nouveaux champs failedLoginAttempts (int, @Builder.Default a 0) et lockedUntil (LocalDateTime, nullable).
- backend/src/main/java/com/creditflow/auth/service/AuthService.java — login() restructure : lookup de l'utilisateur avant l'appel a authenticationManager.authenticate(...) (au lieu d'apres, comme aujourd'hui) pour pouvoir rejeter immediatement un compte verrouille sans relancer BCrypt ; authenticate(...) entoure d'un try/catch(AuthenticationException) qui incremente failedLoginAttempts (et pose lockedUntil si le seuil est atteint) avant de relancer l'exception telle quelle ; en cas de succes, reinitialise failedLoginAttempts/lockedUntil si necessaire. Les commentaires existants sur les frontieres de transaction (etapes 1/2, bean userRepository distinct) doivent etre adaptes au nouvel ordre, pas supprimes : ils restent vrais mais decrivent desormais une etape 0 (lookup + verrou) qui precede l'authentification.
- backend/src/main/java/com/creditflow/config/AppProperties.java — nouvelle classe imbriquee Login sous Security (maxAttempts defaut 5, lockoutMinutes defaut 15), ajoutee via un champ login dans Security.
- backend/src/main/resources/application.yml — sous app.security, bloc login avec max-attempts et lockout-minutes pilotes par variables d'environnement, sur le meme modele que jwt.expiration-minutes.
- .env.example, .env.production.example — nouvelles variables LOGIN_MAX_ATTEMPTS=5, LOGIN_LOCKOUT_MINUTES=15.
- backend/src/test/java/com/creditflow/auth/service/AuthServiceTest.java (existant) — le constructeur d'AuthService ne change pas de signature (pas de nouvelle dependance injectee, properties est deja mocke et fournit desormais aussi getSecurity().getLogin()) ; nouveaux cas : verrouillage apres N echecs, deverrouillage a l'expiration, reset du compteur apres un login reussi, message identique pour compte inexistant, mauvais mot de passe et compte verrouille.

Frontend / infra nginx :
- frontend/nginx/ratelimit.conf (nouveau) — declare limit_req_zone (cle $binary_remote_addr, zone login_zone, 10m, rate 5r/m) et limit_req_status 429. Doit vivre dans le contexte http de nginx, pas server : ne peut donc pas etre ajoute a locations.conf (inclus dans un bloc server, voir http.conf/https.conf) ni aux templates http.conf/https.conf eux-memes (ce sont aussi des blocs server). Sera copie directement vers /etc/nginx/conf.d/ratelimit.conf (voir frontend/Dockerfile), aux cotes de default.conf genere par docker-entrypoint.sh : les fichiers de conf.d/*.conf sont concatenes dans le meme bloc http{} de l'image nginx:1.27-alpine (fichier nginx.conf de base de l'image, absent de ce repo, a verifier explicitement au moment du build, voir Risques).
- frontend/nginx/locations.conf — nouvelle location exacte "location = /api/auth/login" avec limit_req zone=login_zone burst=10 nodelay, qui duplique les proxy_set_header/proxy_read_timeout du bloc location /api/ existant (une location exacte prime sur le prefixe /api/, donc seul /api/auth/login est limite, le reste de l'API n'est pas touche) ; ajoute error_page 429 vers une location interne @api_429 qui renvoie un JSON, sur le meme modele que @api_413 deja present, plutot que la page HTML par defaut de nginx.
- frontend/Dockerfile — nouvelle ligne COPY nginx/ratelimit.conf vers /etc/nginx/conf.d/ratelimit.conf (statique, ne depend pas du mode HTTP/HTTPS, donc copie directement en dehors du mecanisme de templates/entrypoint qui ne gere que default.conf).

Non modifie (verifie explicitement) : AuthController.java (aucune nouvelle route, le controller reste un simple passe-plat), AppUserDetailsService.java, JwtService.java, JwtAuthenticationFilter.java, SecurityConfig.java (le mapping AuthenticationException vers 401 "Identifiants invalides" existe deja et n'a pas besoin d'evoluer), GlobalExceptionHandler.java, V15__row_level_security.sql, V16__app_role_grants.sql.

## Decisions cles

- Verrou par compte, pas par IP, cote applicatif. Le rate limiting nginx protege contre le flood volumetrique depuis une IP donnee ; le verrou applicatif protege le compte ADMIN specifiquement vise par le ticket contre un brute-force distribue (plusieurs IP). Les deux sont complementaires et non redondants, d'ou le choix de garder les deux plutot que de trancher pour un seul niveau comme le suggerait le ticket.
- Aucune nouvelle dependance Maven. Bucket4j (ou equivalent) est absent du pom.xml (verifie) ; le besoin se couvre par deux colonnes plus logique de service, sans etat partage a operer (coherent avec l'absence de Redis dans docker-compose.yml).
- Seuil et duree configurables, pas codes en dur : LOGIN_MAX_ATTEMPTS (5) et LOGIN_LOCKOUT_MINUTES (15), sur le meme modele que les autres reglages operables par variable d'environnement (JWT_EXPIRATION_MINUTES, MAIL_ENABLED, etc.). Valeurs par defaut choisies pour ne pas penaliser un utilisateur legitime qui se trompe une ou deux fois (critere d'acceptation), tout en bloquant un script apres quelques secondes.
- Compteur remis a zero apres verrouillage declenche, pas plafonne indefiniment : au N-ieme echec, lockedUntil est pose et failedLoginAttempts repasse a 0, pour que l'utilisateur beneficie d'un nouveau quota complet des l'expiration du verrou plutot que de rester bloque en boucle par un compteur qui ne redescend jamais.
- Lookup utilisateur deplace avant authenticate() dans AuthService.login(). Necessaire pour pouvoir rejeter un compte verrouille sans meme tenter l'authentification (evite un calcul BCrypt inutile et garde le comportement de verrouillage independant du mot de passe fourni). Consequence directe : la logique et les commentaires actuels sur les frontieres transactionnelles bougent d'endroit sans changer de fond.
- Message d'erreur unique pour les 3 cas d'echec (compte inexistant, mauvais mot de passe, compte verrouille) : reutilisation d'une AuthenticationException standard (LockedException ou BadCredentialsException, a trancher par le spec-writer/codeur), deja mappee en 401 "Identifiants invalides" par GlobalExceptionHandler. Aucune nouvelle classe d'exception dediee au verrouillage n'est necessaire cote HTTP.
- limit_req applique uniquement a location = /api/auth/login, pas au prefixe /api/ global, pour ne pas degrader les autres endpoints (consultation de fiches clients, paiements, etc.) qui peuvent legitimement etre appeles en rafale par l'UI.

## Risques / points d'attention

- Le nginx.conf de base de l'image nginx:1.27-alpine n'est pas dans ce repo : l'hypothese que /etc/nginx/conf.d/*.conf est inclus dans le bloc http{} (comportement standard de cette image officielle, mais non verifiable ici) doit etre confirmee au premier build (docker compose build frontend puis nginx -t dans le conteneur). Si l'image a ete personnalisee differemment, ratelimit.conf echouerait a charger limit_req_zone avant son usage.
- Duplication des directives proxy_set_header entre location /api/ et la nouvelle location = /api/auth/login dans locations.conf : un futur changement de ces en-tetes devra etre reporte manuellement dans les deux blocs. Une alternative avec un snippet partage inclus dans les deux locations a ete ecartee pour limiter le risque de casser le bloc /api/ existant qui fonctionne deja en production.
- rate=5r/m avec burst=10 nodelay est une premiere estimation, pas une valeur mesuree sur le trafic reel de connexion (rechargements de page, onglets multiples d'un meme gerant derriere la meme IP boutique). A valider par le spec-writer/reviewer, quitte a l'assouplir si des faux positifs apparaissent en usage normal.
- Comptes partages derriere une IP commune (boutique avec un seul acces internet) : le rate limiting nginx par IP peut ralentir plusieurs vendeurs de la meme boutique en meme temps si l'un d'eux enchaine les erreurs de frappe. Le verrou applicatif (par compte, pas par IP) n'a pas ce probleme, argument supplementaire pour garder les deux couches independantes plutot que de tout reporter sur nginx.
- AuthService.login() est actuellement bien commente sur ses frontieres transactionnelles (etapes 1/2, beans distincts) : la restructuration doit conserver cette clarte, pas juste deplacer du code. A verifier explicitement en revue.
- Attaque par enumeration de comptes malgre tout possible via timing (une tentative sur un compte inexistant echoue plus vite qu'une tentative sur un compte existant avec mauvais mot de passe, a cause du calcul BCrypt) : risque preexistant, non traite par ce ticket (aucune protection specifique attendue par les criteres d'acceptation), a documenter comme limite connue plutot qu'a corriger ici.

## Hors perimetre

- CAPTCHA ou toute friction visuelle cote frontend : le ticket propose "throttling ou captcha" comme options, celle retenue est le throttling (nginx plus verrou applicatif), pas de captcha.
- Notification ou alerte (email, log centralise) a l'ADMIN en cas de compte verrouille : non demande par les criteres d'acceptation.
- Rate limiting sur les autres endpoints d'authentification (/api/auth/password, /api/auth/logout) ou sur le reste de l'API : le ticket cible explicitement /api/auth/login.
- Correction du canal de timing BCrypt vs utilisateur inexistant (voir Risques) : non demande, documente comme limite connue.
- Deverrouillage manuel anticipe d'un compte par un ADMIN (endpoint dedie) : non demande par le ticket ; le deverrouillage se fait uniquement par expiration du delai.
