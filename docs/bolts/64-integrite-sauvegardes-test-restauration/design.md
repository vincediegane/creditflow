# Design — Issue #64 : intégrité des sauvegardes et test périodique de restauration

## Approche

Deux filets indépendants, tous deux à ajouter sans dépendre du contenu exact du fix de #63 (voir Risques) : (1) une vérification post-sauvegarde (taille plancher + gunzip -t) exécutée juste après l'écriture de chaque archive, dans backup.sh et backup-loop.sh ; (2) un script de restauration de test (scripts/restore-test.sh), autonome et invocable à la demande, restaurant la dernière sauvegarde valide dans une instance PostgreSQL jetable et isolée (jamais la base db de production), avec des vérifications de cohérence minimales (tables clés présentes, migrations appliquées). Un nouveau service sidecar restore-test dans docker-compose.yml, calqué sur le service backup existant, l'exécute automatiquement une fois par semaine via un script restore-test-loop.sh qui n'est qu'un wrapper autour de restore-test.sh (même découpage que backup.sh/backup-loop.sh).

Point important vérifié dans le code actuel : le bug de #63 ne produit pas une archive .gz structurellement corrompue -- pg_dump échoue mais le pipe (pg_dump | gzip -9 > TARGET.part) compresse quand même un flux vide (gzip réussit, son code de sortie est le seul testé par le if actuel), ce qui donne un fichier .gz valide d'environ 20-30 octets. gunzip -t seul ne détecterait donc rien : c'est le plancher de taille qui est le contrôle décisif ici, gunzip -t couvrant en complément la corruption partielle (écriture interrompue, disque plein en cours de compression).

Prix de cette approche : ajouter un service Docker permanent supplémentaire (restore-test) pour un test qui ne s'exécute qu'une fois par semaine, plutôt que de dépendre d'une tâche cron côté hôte (qui n'existe nulle part ailleurs dans ce projet -- aucune trace de cron/systemd timer dans le dépôt, le seul mécanisme de récurrence existant est le patron sidecar-container-en-boucle utilisé par backup/backup-loop.sh). Rester cohérent avec ce patron déjà en place et déjà documenté (README) l'emporte sur l'économie d'un conteneur.

## Fichiers/modules impactés

- scripts/backup-verify.sh (nouveau) -- logique de vérification partagée (taille plancher configurable, gunzip -t), sous forme de script sourcable, appelé juste après le mv final réussi dans backup.sh et backup-loop.sh. En cas d'échec : ne pas laisser le fichier invalide se mélanger aux sauvegardes valides -- le déplacer vers backups/quarantine/ (nouveau sous-dossier, jamais lu par restore.sh qui ne liste que backups/*.sql.gz, ni par restore-test.sh) et logger CRITIQUE.
- scripts/backup.sh -- après le mv "$TARGET.part" "$TARGET" existant (ligne 24), appel à la vérification ; sortie non-zéro + message CRITIQUE si elle échoue (actuellement le script se termine toujours en succès dès que mv réussit).
- scripts/backup-loop.sh -- même ajout après le mv de la boucle (ligne 35), sans interrompre la boucle (while true) : log CRITIQUE puis on continue au prochain cycle, même patron que la branche else déjà présente pour l'échec de pg_dump.
- scripts/restore-test.sh (nouveau) -- un seul restore de test, exécutable manuellement (docker compose exec restore-test restore-test.sh, ou directement dans un conteneur postgres:16-alpine jetable côté hôte) : choisit la dernière archive valide dans backups/ (ignore backups/quarantine/), initialise un serveur PostgreSQL éphémère local (initdb + pg_ctl dans un répertoire non persistant, recréé à chaque exécution), restaure via psql -v ON_ERROR_STOP=1 (contrairement à restore.sh actuel, voir Risques), vérifie la présence des tables clés (organizations, users, credit_sales, installments, payments, flyway_schema_history) via to_regclass et que flyway_schema_history contient au moins une ligne (preuve que les migrations ont bien été rejouées), puis arrête et détruit l'instance éphémère. Code de sortie non-zéro + message CRITIQUE sur tout échec (restauration ou vérification).
- scripts/restore-test-loop.sh (nouveau) -- boucle hebdomadaire (RESTORE_TEST_INTERVAL_HOURS, défaut 168), wrapper fin autour de restore-test.sh, même structure que backup-loop.sh (log horodaté, pas d'arrêt de boucle sur échec).
- docker-compose.yml -- nouveau service restore-test (image postgres:16-alpine, déjà utilisée par db et backup, contient initdb/pg_ctl/psql) : monte ./backups:/backups:ro (lecture seule -- ce conteneur ne doit jamais pouvoir modifier les archives réelles), ./scripts/restore-test-loop.sh et ./scripts/restore-test.sh en :ro, variable RESTORE_TEST_INTERVAL_HOURS. Pas de depends_on: db (ce service ne touche jamais la base de production) et pas de montage du socket Docker (voir Décisions clés).
- .env.example, .env.production.example -- nouvelles variables BACKUP_MIN_SIZE_BYTES (défaut 1024) et RESTORE_TEST_INTERVAL_HOURS (défaut 168), sur le modèle de BACKUP_INTERVAL_HOURS/BACKUP_RETENTION_DAYS déjà présentes.
- README.md -- section Sauvegardes : documenter la vérification automatique post-sauvegarde, la quarantaine, le service restore-test, et compléter la ligne actuelle Testez une restauration avant la mise en service, puis une fois par trimestre (qui décrit aujourd'hui une procédure manuelle) par la mention du test automatique hebdomadaire et de la commande manuelle docker compose exec restore-test restore-test.sh.

Non modifié : scripts/restore.sh (la restauration réelle en production reste un acte humain confirmé par OUI, ce ticket n'y touche pas -- voir Hors périmètre) ; scripts/tenant-export.sh, scripts/tenant-delete.sh (aucune intersection avec ce périmètre).

## Décisions clés

- Plancher de taille : 1024 octets, configurable (BACKUP_MIN_SIZE_BYTES). Les 4 archives réelles présentes dans backups/ sur cette branche font 10,3-11,1 Ko (vérifié : du/ls -lh), largement au-dessus ; la signature du bug #63 (gzip d'un flux vide) donne des fichiers de 20-30 octets (confirmé par le message de la purge a7f6e6a sur la branche #63 : fichiers ~20 octets). 1024 octets sépare nettement les deux cas même sur une base de démo quasi vide (le schéma seul -- RLS, policies, séquences -- dépasse ce seuil en .sql.gz).
- Fichier en échec de vérification -> quarantaine (backups/quarantine/), jamais suppression automatique. Une archive invalide reste une preuve utile pour le post-mortem (comme la purge manuelle documentée dans le commit a7f6e6a sur #63) ; elle ne doit simplement pas pouvoir être confondue avec une sauvegarde exploitable par restore.sh (qui liste backups/*.sql.gz) ni par restore-test.sh.
- Instance de restauration de test = serveur PostgreSQL éphémère lancé dans le conteneur restore-test lui-même (initdb/pg_ctl locaux), pas un conteneur Docker sibling. Alternative écartée : monter /var/run/docker.sock dans un sidecar pour qu'il orchestre un conteneur postgres:16-alpine jetable via docker run/docker compose run -- techniquement plus proche de l'environnement réel, mais donne à ce conteneur un accès équivalent root sur l'hôte (n'importe quel process dans un conteneur avec le socket Docker monté peut monter n'importe quel chemin de l'hôte). Le prix de l'alternative retenue : l'instance de test n'est pas exactement l'image/volume de production (mêmes binaires PostgreSQL 16 alpine, mais pas la même topologie réseau/volume) -- acceptable, l'objectif du ticket est de vérifier que le .sql.gz se restaure et contient les données attendues, pas de répliquer l'infrastructure de prod à l'identique.
- restore-test.sh utilise psql -v ON_ERROR_STOP=1, contrairement à restore.sh actuel qui ne l'a pas (vérifié ligne 48 : gunzip -c "$FILE" | docker compose exec -T db psql -q -U ..., sans -v ON_ERROR_STOP=1). Sans cette option un test de restauration pourrait ignorer des erreurs SQL en cours de route et remonter un faux succès -- inacceptable pour un script dont le seul but est de détecter les échecs. Ne pas modifier restore.sh en production dans ce ticket (voir Hors périmètre) mais le signaler au spec-writer comme incohérence pré-existante à trancher séparément.
- Vérification de contenu = présence de tables clés + flyway_schema_history non vide, pas de comptage de lignes strict sur les données métier. Une instance neuve (première installation chez un client) a légitimement une base vide ou quasi vide ; exiger des lignes dans credit_sales/payments produirait de faux échecs. La preuve recherchée est la restauration s'exécute sans erreur et reconstruit un schéma cohérent, pas il y a des données.
- Aucun canal d'alerte au-delà du log critique. Vérifié : NOTIFICATION_CHANNEL (SMS/WhatsApp/email, module notification) est un canal orienté client final, sans équivalent pour l'exploitation/l'infrastructure ; aucun webhook Slack/PagerDuty n'existe dans scripts/ ou docker-compose.yml. Le ticket demande explicitement une notification si un canal existe déjà -- aucun n'existe, donc le log CRITIQUE (déjà le vocabulaire utilisé par le fix de #63) sur stdout/stderr, visible via docker compose logs backup/docker compose logs restore-test, est le seul livrable réaliste ici.

## Risques / points d'attention

- Risque de conflit de merge avec la PR #70 (fix #63, non mergée). Vérifié directement sur la branche bolt/issue-63-sauvegardes-pgdump-echec-masque-gzip (commit cfd4aa5) : le fix de #63 restructure le même bloc de succès dans backup.sh/backup-loop.sh (écriture pg_dump vers un fichier .sql.raw intermédiaire, puis gzip/mv dans un sous-if séparé) que ce ticket doit également modifier pour y insérer l'appel de vérification. Les deux branches touchent des lignes contiguës autour du mv final. Pour limiter la casse au merge, l'appel à backup-verify.sh doit être inséré comme une ligne quasi-autonome immédiatement après le mv réussi (avant le log OK / echo Sauvegarde terminee), et non imbriqué dans la structure if/else existante -- ce point de conflit est signalé ici, sa résolution reste à faire au merge, pas dans ce ticket.
- scripts/backup.sh et scripts/backup-loop.sh sur cette branche n'ont pas encore le fix de #63 : set -o pipefail n'y existe pas, et le code de sortie de pg_dump dans le pipe n'est pas vérifié. La vérification post-sauvegarde de ce ticket (taille + gunzip -t) est un filet complémentaire qui fonctionne indépendamment de ce bug (elle détecte le symptôme -- fichier anormalement petit -- même si la cause racine n'est pas encore corrigée), donc ce ticket reste utile et livrable même si #63 n'est pas encore mergé. Ne pas essayer de porter le fix de #63 dans cette branche : hors périmètre de #64.
- restore-test consomme de la RAM/CPU une fois par semaine sur la même machine que db/backend (déploiement mono-VM par client, pas d'infra dédiée aux tests visible dans le dépôt) : un initdb + restauration + arrêt sur une base de démo est rapide et léger, mais si un client accumule un volume de données important, le pic hebdomadaire est à surveiller (non chiffrable à ce stade, pas de métrique de taille de base disponible dans le dépôt).
- Aucune sauvegarde valide disponible (première installation, ou toutes les archives récentes en quarantaine) : restore-test.sh doit se terminer proprement en SKIP/log informatif, pas en CRITIQUE -- un CRITIQUE sur il n'y a encore rien à tester serait un faux positif bruyant dès le premier déploiement.
- AC3 (exécution manuelle de bout en bout avant mise en production chez le premier client) est une étape de validation opérationnelle, pas un artefact de code : à documenter comme condition de passage en revue (exécuter réellement restore-test.sh une fois, constater le succès, consigner la preuve -- même exigence de vérification réelle que celle appliquée par le reviewer de #63 sur les scripts de sauvegarde).

## Hors périmètre

- Modifier le comportement de production de scripts/restore.sh (ajout de ON_ERROR_STOP=1, changement de son flux de confirmation) -- seule l'incohérence est signalée en Décisions clés/Risques, la correction éventuelle est un arbitrage séparé.
- Porter ou fusionner le fix de #63 dans cette branche -- les deux tickets restent indépendants jusqu'au merge.
- Un canal d'alerte externe (email/Slack/PagerDuty) pour les échecs de sauvegarde ou de restauration de test -- aucun canal d'exploitation n'existe dans le dépôt ; en créer un serait un chantier à part entière, non demandé par ce ticket au-delà du log critique.
- Sauvegarde/restauration par organisation (tenant-export.sh/tenant-delete.sh) -- ce ticket ne couvre que la sauvegarde/restauration complète de la base (backup.sh/backup-loop.sh/restore.sh).
- Chiffrement, copie hors-site automatique, ou politique de rétention des archives -- non demandés par les critères d'acceptation, déjà couverts par la documentation existante (README, recopie manuelle hors machine).
