# Design — Issue #5 : relances automatiques par SMS/WhatsApp

## Approche

`NotificationChannel` reste l'unique point d'extension (interface inchangée : `name()` / `send(phone, message): boolean`), et on y branche une nouvelle implémentation concrète `WhatsAppCloudApiChannel` (Meta Graph API, via `RestTemplate`), activable par `app.notification.channel=whatsapp` — même mécanisme `@ConditionalOnProperty` que documenté dans le Javadoc actuel de l'interface. Le vrai travail de conception porte sur `ReminderService` : aujourd'hui `generate()` appelle `notificationChannel.send(...)` à chaque prévisualisation, ce qui deviendrait dangereux une fois un canal réel branché (ouvrir la boîte de dialogue de prévisualisation enverrait un vrai message). On découple donc strictement la génération (aperçu, sans effet de bord) de l'envoi (nouvelle action explicite send/send-all, qui appelle réellement le canal et historise le résultat). Le "et/ou fournisseur SMS local" du ticket n'est pas concrétisé : aucun fournisseur SMS n'existe dans le dépôt (pas de dépendance, pas de compte de test, pas de mention dans .env.example), et en choisir un au hasard serait une invention non vérifiable ; le point d'extension est prêt pour un SmsChannel futur suivant exactement le même patron. Prix de cette approche : deux nouvelles actions serveur (send, send-all) en plus de generate, et l'aperçu existant perd son (unique) effet de bord actuel — mais celui-ci n'était de toute façon jamais exploité (canal MANUEL = no-op) et sa suppression est ce qui garantit le critère « pas de régression, repli manuel toujours disponible ».

## Fichiers/modules impactés

Backend :
- backend/src/main/java/com/creditflow/notification/service/WhatsAppCloudApiChannel.java (nouveau) — implémente NotificationChannel, @ConditionalOnProperty(name = "app.notification.channel", havingValue = "whatsapp"), @Component. Construit l'URL {apiBaseUrl}/{apiVersion}/{phoneNumberId}/messages, POST JSON (Authorization: Bearer {accessToken}) via RestTemplate injecté. Catch RestClientException en interne (numéro invalide, quota/429, timeout) puis log et return false, ne relance jamais d'exception (contrat de l'interface : un boolean, jamais un throw côté appelant).
- backend/src/main/java/com/creditflow/config/WebConfig.java — ajoute un Bean RestTemplate avec timeouts connect/read explicites (ex. 5s/10s) ; aucun RestTemplate bean n'existe aujourd'hui dans le projet.
- backend/src/main/java/com/creditflow/config/AppProperties.java — nouvelle classe imbriquée Notification (channel par défaut "manual", sous-classe Whatsapp : phoneNumberId, accessToken, apiBaseUrl défaut https://graph.facebook.com, apiVersion défaut v20.0).
- backend/src/main/resources/application.yml — bloc app.notification.channel lu depuis NOTIFICATION_CHANNEL (défaut manual) et app.notification.whatsapp.* lus depuis WHATSAPP_PHONE_NUMBER_ID / WHATSAPP_ACCESS_TOKEN (vides par défaut, aucun secret en dur).
- .env.example, .env.production.example — nouvelles variables NOTIFICATION_CHANNEL, WHATSAPP_PHONE_NUMBER_ID, WHATSAPP_ACCESS_TOKEN (vides/commentées, manual par défaut).
- backend/src/main/java/com/creditflow/notification/service/ManualCopyChannel.java — expose une constante publique NAME = "MANUAL_COPY" (évite de dupliquer la chaîne dans ReminderService) ; comportement inchangé.
- backend/src/main/java/com/creditflow/notification/service/ReminderService.java — refactor interne : prepareForSale(saleId, template) / prepareForCustomer(customerId, template) (privées) renvoient un petit porteur interne (Customer, BigDecimal amount, String message) sans toucher au canal. generate(ReminderRequest) (inchangé côté API) construit désormais la ReminderResponse directement depuis ce porteur, avec sent = false (aperçu pur, plus d'appel à notificationChannel.send). Nouvelles méthodes : send(ReminderRequest request) (dispatch individuel : garde MANUAL_COPY qui lève une BusinessRuleException, sinon appelle notificationChannel.send, journalise via AuditLogService, renvoie ReminderResponse) et sendAll(String template) (itère lateCustomerService.lateCustomers(), appelle prepareForCustomer et dispatch pour chaque customerId, avec un try/catch par client pour ne jamais interrompre le lot, agrège dans BulkReminderResponse). Nouvelle dépendance : LateCustomerService, AuditLogService.
- backend/src/main/java/com/creditflow/notification/dto/BulkReminderResponse.java (nouveau, record) : total (int), sent (int), failed (int), results (List de ReminderResponse).
- backend/src/main/java/com/creditflow/notification/web/ReminderController.java — POST /api/reminders/send (ReminderRequest vers ReminderResponse) et POST /api/reminders/send-all (vers BulkReminderResponse) ; pas de @PreAuthorize (même exposition que /generate aujourd'hui, ouvert à ADMIN et SELLER, voir Décisions clés).
- backend/src/test/java/com/creditflow/notification/service/WhatsAppCloudApiChannelTest.java (nouveau) — RestTemplate mocké (Mockito), aucun appel réseau réel : cas succès (200), échec HTTP (4xx/429 vers false), exception réseau (RestClientException vers false, pas de throw).
- backend/src/test/java/com/creditflow/notification/service/ReminderServiceTest.java (nouveau, n'existe pas encore) — generate() n'appelle jamais notificationChannel.send ; send() refuse en MANUAL_COPY (BusinessRuleException) ; send() journalise REMINDER_SENT/REMINDER_FAILED via AuditLogService ; sendAll() continue le lot quand un client échoue (client mocké qui lève une exception en position 2 sur 3, vérifie que les 3 sont traités).

Frontend :
- frontend/src/types.ts — nouveau type BulkReminderResult (total, sent, failed en number, results en Reminder[]) ; le type Reminder existant est réutilisé tel quel pour les lignes de résultat.
- frontend/src/api/endpoints.ts — remindersApi.send(payload) (POST /reminders/send) et remindersApi.sendAll(template) (POST /reminders/send-all).
- frontend/src/pages/LateCustomersPage.tsx — bouton d'en-tête « Envoyer les relances » (mutation sendAll, invalide les query keys late-customers et audit-log), visible mais désactivé avec tooltip explicatif si settings.data?.channel vaut MANUAL_COPY ; nouveau bouton par ligne « Envoyer automatiquement » (mutation send avec customerId) à côté de « Générer la relance », même garde de visibilité/désactivation.
- frontend/src/utils/format.ts — AUDIT_ACTION_LABELS : ajoute REMINDER_SENT (Relance envoyée) et REMINDER_FAILED (Échec d'envoi de la relance).
- frontend/src/pages/CustomerDetailPage.tsx — la carte AuditHistoryCard y reçoit déjà un actionLabels qui remplace le défaut (seulement DELETE aujourd'hui) : y ajouter aussi REMINDER_SENT/REMINDER_FAILED, sinon ces entrées s'affichent sous leur clé brute sur cette page précise.

Non modifié (vérifié explicitement) : NotificationChannel.java (interface), ReminderMessageBuilder.java, LateCustomerService.java, LateCustomerResponse.java, tout le module audit (réutilisé tel quel), aucune migration Flyway.

## Décisions clés

- Historisation via audit_log existant, pas de nouvelle table. Le ticket suggère explicitement de s'appuyer sur #2 ; AuditLogService.record(entityType, entityId, entityLabel, action, details) est déjà générique et AuditHistoryCard (déjà branché sur CustomerDetailPage, entityType="CUSTOMER") affichera les nouvelles entrées REMINDER_SENT/REMINDER_FAILED sans nouvel écran. Alternative rejetée : table dédiée reminder_log — plus riche (statut par client visible en liste) mais duplique un mécanisme déjà livré, pour un besoin (historisé avec son statut) que l'audit log couvre déjà entièrement. Effet de bord positif : évite aussi le problème déjà présent dans les migrations (V3__audit_columns.sql et V3__credit_sale_interest.sql partagent le même numéro de version, vérifié dans backend/src/main/resources/db/migration/), donc aucune nouvelle migration n'est nécessaire pour ce ticket.
- generate() découplé de l'envoi réel. Avant ce ticket, ReminderService.respond() appelait déjà notificationChannel.send(...) à chaque génération d'aperçu (sans conséquence tant que seul ManualCopyChannel, un no-op, existait). Une fois un canal réel branché, ouvrir la boîte de dialogue de prévisualisation (ReminderDialog, déclenchée automatiquement à l'ouverture) enverrait un vrai message sans confirmation explicite du gérant. Décision : generate() ne touche plus jamais à NotificationChannel ; seuls les nouveaux endpoints send/send-all déclenchent un envoi réel. Ceci est aussi ce qui garantit mécaniquement le critère « repli manuel disponible même si l'auto échoue » : la prévisualisation, la copie et le lien wa.me restent utilisables en toutes circonstances, indépendamment du canal configuré ou d'un échec précédent.
- Interface NotificationChannel non modifiée (toujours un simple boolean en retour de send, pas de type enrichi avec détail d'erreur). La gestion des échecs (numéro invalide, quota) se fait entièrement à l'intérieur de WhatsAppCloudApiChannel (catch puis false) et par un try/catch défensif supplémentaire autour de chaque client dans ReminderService.sendAll(). Alternative envisagée (retourner un petit objet résultat avec message d'erreur, pour un detail plus riche dans audit_log.details) : rejetée pour respecter littéralement le contrat déjà documenté dans le Javadoc de l'interface (ajouter une implémentation sans toucher au reste du code) ; le détail de l'échec reste dans les logs serveur, audit_log.details se limite à un libellé court type "Canal WHATSAPP_CLOUD_API vers <phone> — échec".
- MANUAL_COPY explicitement refusé par send/send-all (BusinessRuleException, HTTP 400) plutôt que d'appeler ManualCopyChannel.send() et de journaliser un faux échec. ManualCopyChannel reste sinon inchangé et continue de satisfaire l'interface par défaut (matchIfMissing = true). Le frontend n'expose de toute façon pas les boutons d'envoi automatique quand settings.channel vaut MANUAL_COPY (donnée déjà exposée par GET /reminders/settings) : cette garde serveur est un filet de sécurité, pas le chemin principal.
- Pas de nouvelle restriction RBAC. /reminders/generate n'a aujourd'hui aucun @PreAuthorize (accessible ADMIN et SELLER, comme toute la page LateCustomersPage) ; send/send-all gardent la même exposition, car rien dans le ticket ne demande de réserver l'envoi automatique aux ADMIN, et modifier ce périmètre serait une extension non demandée du ticket #1 (RBAC).
- Un seul canal automatique implémenté concrètement (WhatsAppCloudApiChannel), pas de SmsChannel. Le ticket dit « et/ou » ; aucun fournisseur SMS n'est référencé nulle part dans le dépôt (pas de dépendance, pas de variable d'environnement, pas de mention produit) donc en choisir un serait une invention, pas une vérification. Le patron (@ConditionalOnProperty avec havingValue = "sms") reste prêt pour un futur ticket.

## Risques / points d'attention

- Format des numéros de téléphone. Customer.phone (backend/src/main/java/com/creditflow/customer/domain/Customer.java) est un String libre, sans validation ni format imposé à la saisie — les numéros existants ne sont probablement pas au format E.164 attendu par l'API WhatsApp Cloud (+221XXXXXXXXX). Sans normalisation, la majorité des envois échoueront silencieusement (retour false, journalisés REMINDER_FAILED) même avec une configuration correcte. Le codeur doit prévoir une normalisation minimale avant l'appel (indicatif par défaut, suppression des espaces/tirets) — non traité par ce design, à spécifier précisément côté spec-writer.
- Contrainte de fenêtre 24h de WhatsApp Cloud API. Meta interdit l'envoi de texte libre (type text) en dehors d'une fenêtre de 24h suivant le dernier message du client vers la boutique ; en dehors de cette fenêtre (le cas normal pour une relance de recouvrement proactive), seul un message-modèle pré-approuvé par Meta peut être envoyé (type template). ReminderMessageBuilder produit aujourd'hui du texte libre variabilisé, incompatible tel quel avec ce mode. C'est un risque opérationnel réel, pas seulement une limite technique : à faire trancher explicitement par le spec-writer (soit exiger un template Meta approuvé avec les variables actuelles, soit documenter que l'envoi échouera hors fenêtre 24h et que ManualCopyChannel reste alors la seule option fiable).
- Lot d'envoi bloquant. sendAll() boucle en synchrone sur tous les clients en retard dans la même requête HTTP ; sans timeout serré sur RestTemplate (à fixer explicitement dans le bean), un fournisseur lent peut faire dépasser le délai côté frontend/proxy pour l'ensemble du lot. Les timeouts connect/read du RestTemplate doivent rester courts (quelques secondes) précisément pour que l'échec d'un client n'allonge pas excessivement le traitement des suivants.
- Secrets absents par défaut. WHATSAPP_ACCESS_TOKEN et WHATSAPP_PHONE_NUMBER_ID vides ne doivent jamais faire planter le démarrage (contrairement à SecurityDefaultsValidator pour JWT/admin/DB) : tant que app.notification.channel reste manual (défaut), ces valeurs ne sont jamais lues. Si channel=whatsapp est activé avec des identifiants vides, l'échec doit rester local à l'appel HTTP (send() renvoie false), jamais un crash au démarrage — à couvrir par un test.
- Aucun test de sécurité au niveau contrôleur n'existe aujourd'hui pour le module notification (contrairement à AuditLogControllerSecurityTest côté audit) ; comme send/send-all restent ouverts à tout utilisateur authentifié (décision ci-dessus), il n'y a rien à ajouter côté RBAC, mais le codeur doit s'assurer qu'aucune régression n'ouvre ces routes aux requêtes non authentifiées (elles héritent de anyRequest().authenticated() dans SecurityConfig, à ne pas modifier).

## Hors périmètre

- Implémentation d'un canal SMS concret (fournisseur non identifié dans le dépôt) — seule l'extensibilité est préservée, comme documenté ci-dessus.
- Tâche planifiée déclenchant les relances automatiquement (cron) — le ticket demande un déclenchement par le gérant (masse ou individuel), pas d'automatisation temporelle ; aucune dépendance à un scheduler n'est introduite.
- Templates WhatsApp pré-approuvés côté Meta Business Manager (création/soumission) — dépend d'un compte Meta Business réel, hors du périmètre code ; ce design se limite à brancher l'appel API, pas à obtenir l'approbation du contenu.
- Nouvelle table de configuration éditable en base (comme penalty_settings du ticket #4) pour les identifiants API — contrairement à la pénalité, ces identifiants sont des secrets de déploiement (comme JWT_SECRET/ADMIN_PASSWORD), donc application.yml plus variables d'environnement, pas un écran d'administration.
- Multi-canal simultané (envoyer par WhatsApp et SMS pour le même client) — app.notification.channel reste un choix unique, cohérent avec le mécanisme @ConditionalOnProperty déjà en place.
