# Design — Issue #52 : notifications par email — nouveau canal SMTP

## Approche

Destinataires : **les comptes internes (`User`, role SELLER/ADMIN)**, pas les clients (`Customer`). Évènement MVP unique : **notification de création de compte vendeur/gérant** (`UserService.create`). Justification : `UserService.create` ne génère aujourd'hui aucun mot de passe temporaire (vérifié) — le mot de passe est saisi directement par l'ADMIN dans `UserRequest.password()` et communiqué de vive voix/à l'écran ; l'envoyer en clair par email serait une régression de sécurité non demandée par le ticket, donc l'email de bienvenue ne contient jamais de mot de passe, seulement la confirmation de création du compte (identifiant, invitation à se connecter). Ce choix évite aussi le chantier plus lourd et plus risqué de la piste (a) — email de relance client — qui suppose de faire collecter une adresse email à chaque client (`Customer`, protégée par RLS, canal de contact aujourd'hui 100% téléphonique) sans qu'aucun signal produit dans le ticket ne confirme que les clients en ont une. `User` n'est pas couvert par RLS (seule `user_shops` l'est, vérifié dans `V15__row_level_security.sql`), donc ajouter une colonne `email` sur `users` ne touche aucune policy. Prix de cette approche : le critère "au moins un évènement métier concret" est rempli par un évènement à faible volume (création de compte, rare) plutôt que par les relances (plus fréquentes, plus visibles) — acceptable pour un MVP P2 dont le but est de poser le canal SMTP, pas de maximiser son usage immédiat.

## Fichiers/modules impactés

Backend :
- `backend/pom.xml` — ajout dépendance `spring-boot-starter-mail`.
- `backend/src/main/resources/db/migration/V19__users_email.sql` (nouveau) — `ALTER TABLE users ADD COLUMN email VARCHAR(255)` nullable (comptes existants n'en ont pas), pas d'`UNIQUE` (pas de cas d'usage d'authentification par email dans ce ticket, l'identifiant reste `username`).
- `backend/src/main/java/com/creditflow/auth/domain/User.java` — nouveau champ `email` (`@Column(length = 255)`, nullable).
- `backend/src/main/java/com/creditflow/auth/dto/UserRequest.java` — nouveau champ optionnel `email` (`@Email @Size(max = 255)`, pas `@NotBlank` : rester compatible avec les comptes qui n'en fournissent pas).
- `backend/src/main/java/com/creditflow/auth/dto/UserResponse.java` — exposer `email` (nullable) pour que le frontend puisse l'afficher/l'éditer plus tard (hors périmètre de le rendre éditable ce ticket-ci, seulement la création).
- `backend/src/main/java/com/creditflow/auth/service/UserService.java` — `create()` : après `userRepository.save(user)`, si `user.getEmail()` non vide, appelle `emailChannel.send(...)` dans un `try/catch` local (voir Décisions clés — ne jamais faire échouer la transaction sur un échec d'envoi).
- `backend/src/main/java/com/creditflow/notification/service/EmailChannel.java` (nouveau, interface) — `boolean send(String to, String subject, String body)`.
- `backend/src/main/java/com/creditflow/notification/service/SmtpEmailChannel.java` (nouveau) — implémente `EmailChannel` via `JavaMailSender`, `@ConditionalOnProperty(name = "app.mail.enabled", havingValue = "true")`, `@Component`.
- `backend/src/main/java/com/creditflow/notification/service/NoopEmailChannel.java` (nouveau) — implémentation par défaut, `@ConditionalOnProperty(name = "app.mail.enabled", havingValue = "false", matchIfMissing = true)`, `send()` log en `debug` et retourne `false` (même patron que `ManualCopyChannel`).
- `backend/src/main/java/com/creditflow/config/AppProperties.java` — nouvelle classe imbriquée `Mail` (`enabled` défaut `false`, `host`, `port` défaut `587`, `username`, `password`, `from`, `fromName` défaut `"CreditFlow"`), ajoutée au champ racine `private Mail mail = new Mail();`.
- `backend/src/main/java/com/creditflow/config/MailConfig.java` (nouveau) — `@Bean JavaMailSender` conditionné par `@ConditionalOnProperty(name = "app.mail.enabled", havingValue = "true")` (construit un `JavaMailSenderImpl` à partir de `AppProperties.Mail`) ; absent en mode désactivé, donc `SmtpEmailChannel` (qui dépend du bean) ne peut de toute façon pas être instancié si `app.mail.enabled=false` — double garde avec le `@ConditionalOnProperty` du channel lui-même.
- `backend/src/main/resources/application.yml` — bloc `app.mail` (`enabled: ${MAIL_ENABLED:false}`, `host: ${MAIL_HOST:}`, `port: ${MAIL_PORT:587}`, `username: ${MAIL_USERNAME:}`, `password: ${MAIL_PASSWORD:}`, `from: ${MAIL_FROM:}`, `from-name: ${MAIL_FROM_NAME:CreditFlow}`), sur le modèle du bloc `app.notification.whatsapp` existant.
- `.env.example`, `.env.production.example` — nouvelles variables `MAIL_ENABLED=false`, `MAIL_HOST=`, `MAIL_PORT=587`, `MAIL_USERNAME=`, `MAIL_PASSWORD=`, `MAIL_FROM=`, `MAIL_FROM_NAME=CreditFlow` (vides/désactivé par défaut, aucun secret en dur).
- `backend/src/test/java/com/creditflow/notification/service/SmtpEmailChannelTest.java` (nouveau) — `JavaMailSender` mocké : succès, `MailException` catchée vers `false`, jamais de `throw`.
- `backend/src/test/java/com/creditflow/auth/service/UserServiceTest.java` (existant probable, sinon nouveau) — `create()` avec email renseigné appelle `emailChannel.send` ; `create()` reste en succès même si `emailChannel.send` lève une exception non catchée par le mock (vérifie l'isolation).

Frontend (périmètre minimal, non bloquant pour les critères d'acceptation qui sont tous backend) :
- `frontend/src/types.ts` — ajoute un champ email optionnel sur le type User existant.
- `frontend/src/pages/UsersPage.tsx` — nouveau champ optionnel "Email" dans le formulaire de création de compte.

Non modifié (vérifié explicitement) : `NotificationChannel.java`, `WhatsAppCloudApiChannel.java`, `ManualCopyChannel.java`, `ReminderService.java`, `Customer.java`, toutes les migrations V1 à V18, `V15__row_level_security.sql` (aucune policy touchée, `users` n'y est pas soumis).

## Décisions clés

- `EmailChannel` séparé de `NotificationChannel`, pas d'interface commune. Les deux canaux n'ont que le nom en commun sur le plan métier ("notifier quelqu'un") mais des signatures fondamentalement différentes (`send(phone, message)` vs `send(to, subject, body)`) et des cycles de vie indépendants (`NotificationChannel` piloté par `app.notification.channel`, un seul bean actif à la fois ; `EmailChannel` piloté par `app.mail.enabled`, un simple booléen). Forcer une abstraction commune ajouterait de l'indirection pour un bénéfice nul : rien dans le code n'a besoin d'itérer sur "tous les canaux" de façon polymorphe.
- Colonne `email` sur `users`, pas sur `customers`. `users` n'est pas couvert par RLS (V15) : ajout de colonne sans impact policy. `customers` l'est (policy `customers_tenant_isolation` filtre sur `shop_id`, une colonne `email` n'y changerait rien non plus en théorie), mais le choix de destinataire (voir Approche) exclut de toute façon les clients pour ce MVP — la question RLS ne se pose donc pas en pratique ici, documentée uniquement pour couper court à toute ambiguïté si un futur ticket réintroduit l'email client.
- Pas d'email contenant le mot de passe. `UserService.create` ne génère pas de mot de passe temporaire aujourd'hui (le champ vient de `UserRequest.password()`, saisi par l'ADMIN) ; ce ticket ne change pas ce flux (générer un mot de passe aléatoire et forcer son envoi par email serait une extension de périmètre non demandée et un chantier de sécurité à part entière). L'email de bienvenue se limite à une confirmation de création de compte avec l'identifiant, sans secret.
- Échec d'envoi n'annule jamais la création du compte. `UserService.create` reste transactionnel sur la persistance ; l'appel à `emailChannel.send(...)` se fait après `userRepository.save(...)`, entouré d'un `try/catch(Exception)` local qui logge en warn et continue — même patron défensif que `sendAll()` dans `ReminderService` (try/catch par élément, jamais de propagation). Alternative rejetée : envoi asynchrone (`@Async`) — non retenue pour ce MVP, un envoi SMTP synchrone reste de l'ordre de quelques centaines de ms et la création de compte est une opération rare, pas un chemin chaud.
- Désactivé par défaut (`app.mail.enabled=false`), satisfait le critère d'acceptation n°4. Contrairement à `WhatsAppCloudApiChannel` où l'activation se fait via le choix de `app.notification.channel` (un canal actif remplace l'autre), ici `NoopEmailChannel` et `SmtpEmailChannel` sont mutuellement exclusifs via un booléen dédié plutôt qu'une valeur de type "channel" à choix multiple — il n'existe qu'un seul fournisseur SMTP envisagé pour ce MVP (paramètres de connexion SMTP standards, valables en mode relay pour SendGrid/Mailgun/SES).

## Risques / points d'attention

- Le bean `JavaMailSender` doit lui-même être conditionné (`MailConfig`), pas seulement `SmtpEmailChannel` — sinon Spring tenterait de construire un `JavaMailSenderImpl` avec des paramètres vides au démarrage même en mode désactivé. Point à vérifier explicitement en revue de code.
- Aucun crash au démarrage si `MAIL_HOST` est vide alors que `MAIL_ENABLED=true` : contrairement à `SecurityDefaultsValidator` (JWT/admin), aucun validateur de cohérence n'est proposé ici (non demandé par le ticket) — un mauvais couple `MAIL_ENABLED=true` avec `MAIL_HOST` vide échouera silencieusement à l'envoi (log warn), jamais au démarrage. À signaler au spec-writer si un garde-fou façon `PlanConfigValidator` est jugé nécessaire.
- Dépendance Maven nouvelle (`spring-boot-starter-mail`) : vérifier l'absence de conflit de version avec le parent `spring-boot-starter-parent` déjà déclaré au premier build.
- `user.getEmail()` peut être null pour tous les comptes déjà existants (migration additive) et pour tout nouveau compte créé sans email (champ optionnel) : `UserService.create` doit garder l'envoi conditionnel, jamais un envoi systématique qui planterait sur un destinataire absent.
- La validation `@Email` sur `UserRequest.email` n'est qu'une validation de forme, pas de vérification de délivrabilité réelle — un email syntaxiquement valide mais inexistant échouera silencieusement côté SMTP (comportement attendu, cohérent avec le critère "repli silencieux + log").

## Hors périmètre

- Email de relance de recouvrement côté client (`Customer`) — piste (a) du ticket, explicitement écartée pour ce MVP (voir Approche) : aucune colonne email ajoutée à `customers`, `ReminderService`/`NotificationChannel` non touchés.
- Email à la réception d'un paiement — piste (c), non retenue : aucun évènement précis n'est confirmé avec le produit, et l'ajouter en plus de l'évènement retenu doublerait le périmètre sans certitude métier.
- Génération d'un mot de passe temporaire aléatoire pour `UserService.create` — le flux de saisie manuelle du mot de passe par l'ADMIN est inchangé ; seul un message de notification sans secret est ajouté.
- Écran d'administration pour éditer l'email d'un compte existant après création (`PATCH /users/{id}`) — seule la création (`POST /users`) est couverte.
- Validateur de cohérence de configuration façon `PlanConfigValidator` pour la config SMTP — non demandé par les critères d'acceptation, signalé en risque pour arbitrage ultérieur.
- Gestion de bounce, désinscription, tracking d'ouverture — hors sujet d'un MVP d'envoi simple.
